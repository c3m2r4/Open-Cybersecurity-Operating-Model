# Attack Detection Response Matrix (ADRM)

## Purpose

The Attack Detection Response Matrix (ADRM) is the operational realization of MITRE ATT&CK for a specific organization. While MITRE ATT&CK lists every possible technique an adversary *might* use, the ADRM documents exactly what *this* organization expects to see, detect, and do when a specific technique is used.

> ATT&CK is the encyclopedia. The ADRM is the organization's specific defensive playbook.

---

## Structure of the ADRM

For every prioritized ATT&CK technique, the ADRM tracks the following defensive state:

| Field | Definition |
|---|---|
| **Tactic / Technique** | The MITRE ATT&CK ID (e.g., T1003.001). |
| **Technique Name** | e.g., OS Credential Dumping: LSASS Memory. |
| **Expected Telemetry** | What specific logs *must* be generated by this activity? (e.g., Sysmon Event ID 10 with TargetImage `lsass.exe`). |
| **Telemetry Status** | Confirmed / Missing / Partial. |
| **Detection Rule ID** | The internal SIEM/EDR rule ID designed to catch this. |
| **Detection Status** | Validated / Theoretical / Tuning Required / Missing. |
| **Expected Response** | What should the SOC or automated systems do? (e.g., Isolate host via EDR). |
| **Last Validated** | Date of the last Purple Team or automated BAS test proving this works. |

---

## Using the ADRM in Operations

The ADRM is the central ledger connecting multiple teams:

1. **Threat Intelligence** identifies a new technique used by a relevant threat actor.
2. **Detection Engineering** checks the ADRM. Is this technique covered? If not, they build a rule and update the ADRM to "Theoretical".
3. **Purple Team** executes the technique. They confirm telemetry, confirm detection, and update the ADRM to "Validated".
4. **SOC** uses the ADRM to know exactly what response playbook applies to the alert.
5. **Management** views the ADRM as a heatmap to understand the organization's true detection coverage against specific threats.

## Example Entry: Kerberoasting

| Field | Value |
|---|---|
| **Tactic** | Credential Access |
| **Technique** | T1558.003 - Kerberoasting |
| **Expected Telemetry** | Windows Security Event ID 4769 (Kerberos Service Ticket Requested). |
| **Telemetry Status** | **Confirmed** (Domain Controllers log this and forward to SIEM). |
| **Detection Rule ID** | `UC-AD-012: High Volume Service Ticket Requests (RC4)` |
| **Detection Status** | **Validated** |
| **Expected Response** | Playbook `IR-PB-008`. Isolate source workstation. Reset service account passwords. |
| **Last Validated** | 2026-07-15 (Automated BAS) |
| **Notes** | Exclusions applied for authorized vulnerability scanner IP. |

## Gap Analysis and Prioritization

When the ADRM identifies a gap, use risk to prioritize it.

| Gap Type | Description | Priority | Action |
|---|---|---|---|
| **Telemetry Gap** | We do not have the logs to see this technique. | High (if technique is critical) | Deploy new logging agent or configure auditing. |
| **Detection Gap** | We have the logs, but no rule alerts on it. | Medium | Add to Detection Engineering sprint backlog. |
| **Validation Gap** | We have a rule, but it has never been tested. | High | Schedule Purple Team execution or add to BAS. |
| **Response Gap** | The alert fires, but the SOC has no playbook for it. | Medium | Develop incident response playbook. |
